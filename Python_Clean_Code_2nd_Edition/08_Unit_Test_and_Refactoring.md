## 1. 단위 테스트

**단위 테스트 (Unit Test)** 는 **다른 코드의 일부분이 유효한지를 검사하는 코드** 이다.

* 단위 테스트가 가져야 하는 특징은 다음과 같다.

| 특징                      | 설명                                                                                                          |
|-------------------------|-------------------------------------------------------------------------------------------------------------|
| 격리 (isolation)          | 비즈니스 로직에 집중해야 하며, **DB 접속, HTTP 연결 등을 하지 않아야** 한다.                                                          |
| 성능 (performance)        | **신속하게 실행** 되어야 하며, 반복 실행이 가능해야 한다.                                                                         |
| 반복 가능성 (repeatability)  | **객관적이고 결정적 (deterministic)** 인 방식으로 테스트해야 한다.<br>- 즉, 같은 코드에 대해 **테스트 통과** 또는 **테스트 실패** 라는 결과가 일관적이어야 한다. |
| 자체 검증 (self-validating) | 단위 테스트 실행만으로 테스트 결과가 **최종 결정** 되어야 한다.                                                                      |

### 1-1. 단위 테스트와 소프트웨어 설계

* **테스트 용이성 (Testability)** 은 **소프트웨어를 얼마나 쉽게 테스트할 수 있는지** 를 의미하며, 클린 코드의 핵심 가치 (= 품질 기준) 에 해당한다.
* 단위 테스트는 **실제 코드 작성 방식에 영향** 을 미치며, 다음 단계를 포함한다.
  * 단위 테스트의 필요성 발견
  * 더 좋은 (나은) 코드 작성
  * **TDD (Test-driven design) = 모든 코드가 테스트에 의해 작성**

## 2. 다른 형태의 자동화 테스트

* **테스트 스위트 (test suite)** 는, **함수/메서드가 아닌 클래스를 테스트** 하기 위해 사용되는 **단위 테스트의 집합** 이다.
* 인수 테스트, 통합 테스트

| 구분     | 설명                                           |
|--------|----------------------------------------------|
| 인수 테스트 | use case를 통해 **사용자 관점에서 시스템 유효성 검사**         |
| 통합 테스트 | **한번에 여러 개의 컴포넌트** 를 테스트하며, 종합적으로 잘 작동하는지 검증 |

## 3. 소프트웨어 테스트의 경계

* 소프트웨어 테스트의 범위는 **우리가 작성한 코드로 한정** 해야 한다.
  * 서드 파트 라이브러리 등을 테스트하는 것은 우리의 책임이 아니고, 해당 라이브러리 개발자의 책임이다.

## 4. 소프트웨어 테스트 도구

* 단위 테스트를 작성하기 위해 사용되는 Python 라이브러리는 다음과 같다.
  * [unittest](https://docs.python.org/3/library/unittest.html) (Python 표준 라이브러리)
  * [pytest](https://docs.pytest.org/en/latest/) (pip 을 통해 설치해야 하는 서드 파티 라이브러리)

* 각 라이브러리의 특징 및 용도는 다음과 같다.

| 라이브러리    | 특징                            | 용도                        |
|----------|-------------------------------|---------------------------|
| unittest | 테스트 시나리오를 위한 다양한 helper 기능 제공 | 테스트 시나리오 다루기              |
| pytest   | fixture (패치 객체) 등 복잡한 옵션 제공   | 의존성이 많은 테스트 (외부 시스템 연결 등) |

* 추가 개념
  * **테스트 파라미터화 (parameterized test)** 는 하나의 테스트 케이스에 적절한 옵션을 넣는 방식을 통해 중복된 테스트 코드를 방지하는 것이다.
  * **픽스처 (fixture)** 는 테스트 케이스를 파라미터화하는 도구이다. (의존성이 있는 테스트에 적합)

## 5. 코드 커버리지 높이기

테스트 코드로 커버되지 않은 코드의 범위를 줄이는 (= 코드 커버리지를 높이는) 방법은 다음과 같다.

* 단위 테스트 추가 작성
* 기존 단위 테스트가 커버하는 범위 확대
* 코드 단순화 및 간결화 (중복 코드 제거 등)
* 도달할 수 없는 (unreachable) 코드를 안전하게 제거

참고로, **커버리지가 높은 것이 항상 좋은 것은 아니므로, 커버리지 향상만을 목표로 하면 안 된다.**

* 프로젝트에서 기대하는 코드 커버리지 (예: 80%) 를 정할 수 있다.
* 높은 코드 커버리지의 코드가 항상 건강한 코드인 것도 아니다. (코드 커버리지는 대부분 **실행된 line의 비율** 이고, **적절히 테스트된 line의 비율이 아니다.**)

## 6. 리팩토링

**리팩토링 (refactoring)** 은 **동작 변경 없이 내부 표현을 재정비하여 코드 구조를 바꾸는** 것이다.

* 리팩토링을 하는 경우의 예
  * 매우 긴 메서드가 있는 경우  
* 리팩토링을 **FM대로 하기 위해서는 '단위 테스트'를 실시** 해야 한다.
  * 코드가 변경될 때에도 여전히 올바른 코드인지를 파악해야 하기 때문이다.
* 리팩토링 시 유의할 점
  * 원래의 인터페이스 변경 금지
  * public 메서드를 이전과 같이 유지
  * 함수의 서명 유지

클린 코드의 목표는 다음과 같다.

* **유지보수 가능** 한 코드
* **요구 사항을 더 많이 수용** 할 수 있는 코드
* **확장 가능한 구조로 리팩토링** 가능한 코드

코드의 유연성이 중요한 이유는 **요구사항은 시간의 흐름에 따라 변화, 진화** 할 수 있기 때문이다.

## 7. 단위 테스트에 대한 추가 사항

단위 테스트에 대해서 다음과 같은 질문을 할 수 있다.

* 단위 테스트를 통해 코드에 대한 확신을 얻을 수 있는데 **그것만으로 충분한가?**
* 테스트는 **누가 실시해야** 하는가?

속성 기반 테스트, 변형 테스트의 의미는 각각 다음과 같다.

| 테스트                             | 의미                                                            | 관련 라이브러리         |
|---------------------------------|---------------------------------------------------------------|------------------|
| 속성 기반 테스트 (Property-based test) | **테스트를 실패하게 만드는** 데이터 찾기                                      | ```hypothesis``` |
| 변형 테스트 (Mutation test)          | 원래 코드를 **새로운 버전 (돌연변이)** 으로 수정하여 테스트<br>- 예: 비교 연산자 변경, 조건 변경 | ```mutpy```      |

## 8. 테스트 관련 추가 논의 사항

* 소프트웨어 테스트를 할 때는 **경계 값/한계 값 (boundary value)** 을 사용하는 것이 좋다.
  * 예를 들어 ```if height >= 180:``` 이라는 조건문이 있다면, ```height```의 값으로 ```179```, ```180``` 등을 테스트한다.
* **등가 (equivalence) 클래스** 는 동일한 확인 결과를 갖는 그룹이다.
  * 여기서 '클래스'는 객체 지향에서의 class 개념이 아닌, '분류' 개념이다.
  * 예를 들어, 위 ```if height >= 180:``` 에서 ```height``` 의 값으로 ```1``` ```2``` ... ```179``` 는 등가 클래스에 해당한다.
  * 등가 클래스 (집합) 내의 원소 중 **하나를 대상으로만 테스트** 해도 된다.
* **엣지 케이스 (edge case)**
  * 예를 들어 날짜를 다루는 로직을 테스트할 때 ```2월 29일``` 등이 이에 해당한다.
* **테스트 주도 개발 (TDD, Test-Driven Development)**
  * **테스트 케이스를 먼저 작성** 한 다음 코드를 작성하는 것을 의미한다.
  * 테스트 주도 개발의 일반적인 순서는 다음과 같다.

```
1. 단위 테스트 작성
2. 최소한의 코드 수정
3. 코드 리팩토링 후, 테스트가 여전히 작동하는지 확인
```
