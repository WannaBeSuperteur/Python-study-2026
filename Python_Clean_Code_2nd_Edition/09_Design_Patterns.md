## 1. Python의 디자인 패턴

* 고전적인 디자인 패턴 중 일부는 **Python에서는 필요하지 않다.**
  * 단, 그 이유는 **해당 디자인 패턴이 Python 내부적으로 구현되어 있기** 때문이다.
* 디자인 패턴은 **발명** 이 아닌 **발견** 되는 것이다.

## 2. Python의 디자인 패턴의 분류

Python의 디자인 패턴은 대표적으로 **생성, 구조, 행동 패턴** 으로 분류된다.

| 구분              | 설명                                       |
|-----------------|------------------------------------------|
| 생성 (creational) | **객체 인스턴스화 시 복잡성을 추상화** 하기 위한 패턴         |
| 구조 (structural) | 인터페이스를 복잡하게 하지 않으면서, **기능을 확장** 하기 위한 패턴 |
| 행동 (behavioral) | 객체 간의 협력/통신, 런타임 중 인터페이스의 형태 등에 대한 패턴    |
| 기타              | 생성, 구조, 행동 패턴을 **확장 또는 변형시킨 추가 패턴**      |

### 2-1. 생성 (creational) 패턴

* 생성 패턴에는 다음과 같은 것들이 있다.

| 구분                   | 설명                                                                                                                        | 추천 여부     |
|----------------------|---------------------------------------------------------------------------------------------------------------------------|-----------|
| 싱글턴 패턴               | 호출 횟수 무관하게 **항상 동일한 객체를 제공하는 클래스** 를 만드는 패턴                                                                               | 낮음        |
| 모노 스테이트 패턴 (SNGMONO) | 일반 객체처럼 **많은 인스턴스 생성** 가능 (싱글턴 여부 무관)<br>- **공유 상태 (shared state)** 를 사용할 수 있다.<br>- 디스크립터 사용 시, 단일 책임 원칙 준수 가능 + 재사용성 확대 | 싱글턴 대비 높음 |
| borg 패턴              | 같은 클래스에서는 **모든 인스턴스가 모든 속성을 복제**<br>- 이로 인한 부작용 고려 필요                                                                     | 싱글턴 대비 높음 |
| 빌더 패턴                | 필요한 모든 객체를 생성하기 위한, **복잡한 객체를 생성** 한다.<br>- 보조 객체 직접 생성이 아닌, **한번에 모든 것을 처리하는 추상화** 필요                                    |           |

### 2-2. 구조 (structural) 패턴

* 구조 패턴에는 다음과 같은 것들이 있다.

| 구분              | 설명                                                                                                                                                                                  | 추천 여부 |
|-----------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-------|
| 어댑터 패턴          | 새로운 객체 (수정 권한 없음, 외부 라이브러리 등) 를 사용하는 대신, **해당 객체를 수용하기 위한 인터페이스 개발**<br>- 방법 1. 기존 클래스를 상속받는 **새로운 클래스** 생성<br>- 방법 2. 컴포지션 사용<br>- 방법 3. ```__getattr__()``` 사용 (일반화된 어댑터)         |       |
| 데코레이터 패턴        | 객체에 **일련의 연산 (데코레이션)** 을 정의                                                                                                                                                         |       |
| 파사드 (Facade) 패턴 | 객체 간 상호 작용을 위한 **허브/연결점 또는 단일 참조점 (single point of reference)** 역할을 하는 '파사드'를 만든다.<br>- 1개의 객체와 N개의 객체를 연결할 때, **N개의 인터페이스 대신 파사드를 사용** 할 수 있다.<br>- 장점: 객체 간 결합력 감소, 인터페이스 개수 감소 등 | 높음    |

* 데코레이터 패턴 예시

```Python
>>> class DivisorCalculator:
	def __init__(self, value: int):
		self.value = value
	def calculate(self):
		divisors = []
		for i in range(1, self.value + 1):
			if self.value % i == 0:
				divisors.append(i)
		return divisors

	
>>> class PrimeChecker(DivisorCalculator):
	def calculate(self):
		divisor_list = super().calculate()
		return len(divisor_list) == 2
```

```python
>>> dc = DivisorCalculator(value=2028)
>>> print(dc.calculate())
[1, 2, 3, 4, 6, 12, 13, 26, 39, 52, 78, 156, 169, 338, 507, 676, 1014, 2028]
>>> pc = PrimeChecker(2027)
>>> print(pc.calculate())
True
>>> pc2 = PrimeChecker(2026)
>>> print(pc2.calculate())
False
```

## 2-3. 행동 (behavioral) 패턴

* 행동 패턴에는 다음과 같은 것들이 있다.

| 구분                                 | 설명                                                                                                                      | 추천 여부           |
|------------------------------------|-------------------------------------------------------------------------------------------------------------------------|-----------------|
| 책임 연쇄 패턴 (chain of responsibility) | 어떤 로직에 대한 처리가 가능한 경우 그 결과를 반환하되, **처리가 불가능한 경우 후계자 (successor) 라는 이벤트 객체에게 전달**<br>- 후계자의 후계자, ... 등 이런 식으로 계속 반복       |                 |
| 템플릿 메서드 패턴                         | 어떤 행위의 정의를 위한, **특정 형태의 클래스 계층 구조** 를 만든다.<br>- 전체 로직은 본 클래스의 템플릿 메서드, 세부 로직은 파생 클래스의 메서드에서 처리하여 **핵심 로직, 세부 로직 분리** 가능 | 적절히 구현 시 중요한 이점 |
| 커맨드 패턴                             | 수행해야 할 작업에 대해, **요청과 실제 실행을 분리**<br>- 커맨드 (명령) 는 **정의된 이후 수정이 가능** 하다.<br>- 실제 커맨드 실행 시에는 ```do``` 메서드를 사용할 수 있다.       |                 |
| 상태 패턴                              | 상태를 문자열이나 숫자 값 등이 아닌 **별도의 객체 (클래스)** 로 만드는 것<br>- 상태 별 객체를 만들어서, **각 객체의 책임을 적게** 하는 것이 좋음<br>- **상태 전이** 를 고려해야 함     |                 |
